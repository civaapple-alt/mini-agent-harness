# 03 上下文与状态：模型看见什么，系统记住什么

“模型知道项目里的哪些信息？”和“服务重启后能恢复什么？”听起来像同一个问题，其实属于两种不同边界。前者关乎一次模型请求的上下文；后者关乎 App Server 和 SessionStore 持久化了哪些运行状态。把二者分开，才能解释为什么模型上下文可以压缩，而一个结果未知的工具调用不能靠重跑来恢复。

## 一次模型请求由什么组成

模型请求通常包含稳定的系统提示、对话消息、工具规格，以及本轮运行时追加的动态上下文。Host 会准备工作区状态、Session 能力和可用 Skill 目录；某些工作区说明则在访问相关文件时才按需注入。Core 将这些输入放进有界请求里，再调用所选模型。

Host 会把当前操作系统、工作区和可用开发工具整理成有界环境快照。macOS 上也能识别常见开发工具和 Blender 项目。快照帮助模型了解它正在什么环境里工作，但不会扫描整台机器，也不授予执行权限。

Skill 目录先提供名称、来源和用途简介。模型按任务选择相关技能，再按需读取正文，而不是一次加载整个技能组。不能被模型主动选择的技能仍可由用户明确调用。项目、个人、内置和插件技能保持来源区分；项目技能的编辑遵循普通工作区写入规则。

模型请求和工具结果都有明确的大小与数量上限，避免单次工作占用过多内存或把大段数据塞进上下文。序列化字节上限是运行时保护措施，不等于模型的 token 窗口；不同模型的实际窗口仍要依据其使用情况判断。

如果工具结果更大，Host 可以将结果保存成 Session artifact，并把有界预览和读取句柄交给模型。这样模型能按页读取所需部分，而不是把完整日志或文件一次塞进上下文。

## 动态上下文有来源，也有版本

项目说明、Skills、工作区状态等动态内容作为消息追加到 Session 历史。相同来源指纹不会重复追加；来源变化时，新版本会记录它替代的旧指纹。压缩历史后，运行时仍能识别每个来源槽位当前有效的版本。

Web Studio 可以展开查看上下文来源和用途，但不另行决定模型上下文或授权。用户能知道本轮带入了哪些材料，运行时仍是实际请求的唯一来源。

## 压缩历史时，最近工作仍然可读

序列化字节上限和模型 token 窗口解决不同问题。运行时不会仅因为 JSON 请求达到某个固定百分比就压缩历史。

在 `Compact` 模式中，Core 根据模型实际报告的用量判断是否需要为后续请求整理历史。窗口信息不足时不猜一个比例；如果提供方明确报告上下文超限，运行时也会尝试有界压缩后重试。

压缩优先保留当前有效的上下文和最近工作，把较早内容整理成摘要；若摘要无法帮助缩小请求，则删减较早历史。它只改变之后发给模型的内容，不会改写 App Server 保存的会话与执行记录。

## 两种 checkpoint，两个恢复问题

| 记录 | 写入时机 | 用途 |
| --- | --- | --- |
| Session checkpoint | Turn 结算后 | 给下一次 Turn 和 Child fork 提供已结算的对话上下文。 |
| Execution checkpoint | 一个逻辑 Turn 执行期间，在模型请求前和工具批次后 | 保存当前输入、消息、下一模型步骤和已记录工具结果，以便操作者核对后显式恢复。 |

执行记录会保存当前任务的进展和已知工具结果。如果进程在副作用发生后、结果保存前退出，系统无法判断文件或命令是否已经改变状态。恢复时不会重放这类调用，而是请操作者核对；全部未知结果处理后，再由用户明确选择是否继续原任务。

停止发生在一组工具调用中时，尚未开始的调用会被跳过，已开始的调用则保留真实结果。副作用不明的结果仍需核对，不能因为收到停止请求就当作没有执行。

纠偏内容也会随执行进度保存。重启后，用户可以确认它是否已经进入模型上下文；仍未应用的纠偏会随用户明确恢复原任务而继续处理。事件回放不负责重建会话正文。

因此，心跳超时、连接断开、取消被接纳，都不等同于进程已经退出或副作用未发生。可靠恢复必须依据 checkpoint 序号、工具调用身份和 App Server 的持久状态。

## Web Studio 怎样显示有界历史

浏览器打开会话时先读取最新活动，用户向上浏览时再加载更早历史。重连后，Studio 会合并重复内容并与运行时保存的会话和执行状态对账；实时事件用于更新界面，不会被当作完整历史。

这种设计同时限制单次读取规模和客户端内存，也避免把事件缓存误当成完整历史。界面断线重连后，先对账当前 Project、Thread、Turn 和运行状态，再决定哪些操作可用；它不会因为没收到事件就把 Session 标为空闲。
